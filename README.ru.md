# VM IOPS Manager

[English](README.md) | Русский

Инструмент для управления лимитом IOPS на дисках виртуальных машин в vCenter
8, где эту возможность убрали из UI. Замена [PowerShell/WinForms-скрипта](https://github.com/Alexaldonov/vSphere-8-IOPS-Manager):
один exe (~14 МБ), без установки PowerCLI, запускается за секунду,
интерфейс — веб-страница, открывающаяся в браузере по умолчанию.
Функционал расширен, по сравнению с моей старой утилитой.
Также совместима с vCenter 7.

## Как это работает

1. `vm-iops-manager.exe` поднимает HTTP-сервер только на `127.0.0.1` на
   случайном свободном порту и открывает браузер по умолчанию на
   `http://127.0.0.1:<port>/?token=<одноразовый токен>`.
2. Все API-запросы страницы требуют этот токен (заголовок `X-Auth-Token`),
   плюс сервер проверяет заголовок `Host`. Это важно при работе на терминальном
   сервере: без токена и с чужим `Host` запрос отклоняется (403), поэтому
   другие залогиненные на той же машине пользователи не смогут обратиться
   к вашему локальному серверу и вашей сессии в vCenter.
3. Закрыли вкладку/браузер — просто откройте ссылку из консоли ещё раз,
   либо перезапустите exe (порт и токен каждый раз новые).
4. К одному запущенному инструменту можно подключить сразу несколько
   vCenter и переключаться между ними кликом по «таблетке» в верхней
   панели — переподключаться не нужно.
5. Сессия к vCenter, как обычно, истекает после периода бездействия
   (обычно ~30 минут). Как только это происходит, первое же действие
   вернёт ошибку — инструмент сам уберёт неживое подключение и откроет
   форму подключения с уже заполненными адресом и логином, останется
   ввести пароль.

## Запуск

Просто запустите `vm-iops-manager.exe`. Откроется консольное окно с
адресом (на случай, если браузер не откроется сам) и браузер с
интерфейсом. Закрытие консольного окна останавливает сервер.

Никакой установки, PowerShell и PowerCLI не требуется — весь код запроса
к vCenter ([govmomi](https://github.com/vmware/govmomi), официальная Go-библиотека VMware) зашит в exe.

## Возможности интерфейса

- Интерфейс на русском или английском — переключатель языка (RU/EN) в
  правом верхнем углу, выбор запоминается в браузере. По умолчанию язык
  определяется по языку браузера.
- Подключение к нескольким vCenter одновременно, быстрое переключение
  между ними без повторного ввода пароля.
- Поиск ВМ по подстроке имени (без учёта регистра) или по точному VM ID
  (moref, например `vm-1234`).
- Таблица дисков найденной ВМ с текущим лимитом IOPS, SCSI/SATA/NVMe-адресом
  в привычном виде `(bus:unit)` (например, `Hard disk 1 (0:0)`) и типом
  контроллера (LSI Logic SAS, VMware Paravirtual, NVMe и т.д.) — то же самое,
  что видно в vSphere Client при выборе диска.
- Изменение лимита отдельного диска (значение `-1` = без лимита).
- Кнопка «Сбросить все лимиты» — снимает лимиты со всех дисков ВМ одним
  запросом `ReconfigVM_Task` (все диски передаются в одном вызове).
- Вкладка «Resource Pool»: поиск resource pool по подстроке имени (с
  указанием кластера/хоста-владельца, чтобы не путать одноимённые пулы),
  просмотр списка ВМ и кнопка «Сбросить лимиты у всех ВМ» — массовый сброс
  лимитов сразу по всем ВМ пула. **В пул попадают только ВМ, лежащие в нём
  непосредственно** — ВМ во вложенных resource pool не учитываются и не
  затрагиваются (сделано намеренно: иначе по ошибке выбранный верхний пул
  мог бы задеть тысячи ВМ во вложенных пулах). Каждая ВМ обрабатывается
  отдельным `ReconfigVM_Task` (до 3 одновременно, чтобы не создавать
  всплеск нагрузки на ESXi), после завершения показывается сводка и
  список ВМ, на которых сброс не удался (если такие есть).
- Вкладка «Датастор»: поиск датастора по подстроке имени, просмотр таблицы
  ВМ и их дисков, лежащих именно на этом датасторе (диски той же ВМ на
  других датасторах в таблицу не попадают), и кнопка «Сбросить лимиты на
  этом датасторе» — точечный сброс только этих дисков. Сценарий: нужно
  срочно перевести датастор в maintenance mode, и снятые лимиты ускоряют
  миграцию (Storage vMotion) именно его дисков, не трогая остальные диски
  тех же ВМ. Список ВМ строится через собственное свойство датастора `vm`
  (все ВМ, у которых на нём есть хоть один файл), поэтому не требует
  перебора всех ВМ vCenter.
- Журнал действий: все изменения лимитов (кто — по логину подключения,
  что именно и когда) построчно печатаются в консольное окно exe. Своей
  истории/базы инструмент не ведёт — это просто поток в stdout, смотрите
  его или перенаправляйте в файл при необходимости
  (`vm-iops-manager.exe > log.txt 2>&1`, либо `... | tee log.txt`, если
  нужен вывод и на экран, и в файл).
- Вкладка «Проверка файлов»: вставляете список путей к `.vmx`/`.vmdk` (по
  одному в строке) и получаете для каждого статус: используется (с именем
  ВМ) или **ZOMBIE** — не зарегистрирован ни за одной ВМ. Аналог PowerCLI команд
  `Get-VM | Get-HardDisk | Where-Object { $_.Filename -eq "..." }` для
  vmdk и `Get-VM | Where-Object { $_.ExtensionData.Config.Files.VmPathName
  -eq "..." }` для vmx, только по всему списку сразу: сначала вся
  инвентаризация ВМ проходится один раз (строится индекс путей), затем
  все переданные пути проверяются по этому индексу — не по одному
  сканированию на каждый путь. Сравнение регистронезависимое, как
  оператор `-eq` в PowerShell. Ограничение: для vmdk учитывается только
  текущий (верхний) файл в цепочке снапшота, как и `$_.Filename` у
  `Get-HardDisk` без обхода цепочки delta-файлов.
  Отдельно проверяется, что сам датастор из `[имя]` вообще существует в
  этом vCenter — если нет (например, отчёт сделан для другого vCenter или
  датастор давно выведен из эксплуатации), путь помечается «датастор не
  найден в этом vCenter», а не ошибочно как ZOMBIE.
  Если датастор найден, дополнительно проверяется физическое наличие
  самого файла на датасторе (через `HostDatastoreBrowser`, как в vSphere
  Client при просмотре файлов датастора). Если файла там нет — путь
  помечается «файл не найден на датасторе» (скорее всего, опечатка в
  пути или файл уже удалён), и только если файл физически есть, но не
  числится ни за одной ВМ — это ZOMBIE.

## Технические детали

- Язык: Go, библиотека для работы с vCenter — `govmomi` (официальный SDK
  VMware/Broadcom для Go).
- Пароли нигде не сохраняются — только логин/пароль в момент подключения,
  сессия живёт в памяти запущенного процесса.
- По умолчанию используется соединение с игнорированием невалидного
  SSL-сертификата (аналог `Set-PowerCLIConfiguration -InvalidCertificateAction
  Ignore` в исходном скрипте) — при необходимости чекбокс в форме
  подключения можно снять.
- Каждое изменение лимита — отдельный вызов `ReconfigVM_Task`, синхронно
  дожидается завершения таска перед тем как показать результат.

## Сборка из исходников

Установлен Go 1.24+ (либо `GOTOOLCHAIN=auto`, тогда Go сам подтянет нужную
версию):

```
go mod tidy
GOOS=windows GOARCH=amd64 go build -ldflags="-s -w" -o vm-iops-manager.exe .
```

Файлы:
- `main.go` — старт HTTP-сервера, токен, открытие браузера.
- `vcenter.go` — вся логика работы с vCenter через govmomi (подключение,
  поиск ВМ/пулов/датасторов, чтение и изменение лимитов дисков, журнал
  действий через `logAction`).
- `api.go` — REST API поверх `vcenter.go`.
- `web/index.html` — вся статика интерфейса (HTML/CSS/JS одним файлом),
  вшивается в exe через `go:embed`.

## Возможные доработки

- Индикатор в результатах поиска, что у ВМ сейчас снят(ы) лимит(ы) — можно
  проверять `StorageIOAllocation.Limit == -1` по всем дискам и подсвечивать
  строку.
- Фильтр по кластеру/resource pool/датастору, если поиск по подстроке
  имени станет возвращать слишком много совпадений.
- Кнопка «Показать shares/reservation» — в API уже есть все нужные данные
  на уровне `StorageIOAllocation`, в текущей версии осознанно не выводится
  (не требовалось для рабочего сценария временного снятия лимитов).
